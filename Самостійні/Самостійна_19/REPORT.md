# Звіт до самостійної роботи №19

## Власний виняток

`InsufficientFundsException` успадковує `Exception`. Він має властивості `RequestedAmount` (скільки хотіли зняти) і `CurrentBalance` (скільки є на рахунку), а також три стандартні конструктори: без параметрів, з `message` і з `message` та `innerException`. Четвертий конструктор приймає ще й суму та баланс. У `Main` метод `Withdraw` кидає цей виняток, а блоки `catch` йдуть від специфічного до загального, після них є `finally`.

## Сценарій 1. Retry з exponential backoff (зовнішній API)

**Проблема.** Сервіс курсів валют інколи відповідає помилкою 503 на кілька секунд і потім сам відновлюється.

**Стратегія і чому.** Retry з експоненційною затримкою та jitter. Збій короткий, тому повторна спроба має шанс успіху. Затримка зростає (0.5 с, 1 с, 2 с), щоб не заважати сервісу відновитись. Jitter додає випадкову складову, щоб багато клієнтів не повторювали запит в один і той самий момент. Повторюємо лише `HttpRequestException`, а інші помилки пробивають політику одразу.

**Код:**

```csharp
var retryPipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(500),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args => { /* лог спроби */ return default; }
    })
    .Build();
```

**Вивід.** Перші два виклики API завершуються помилкою, перед кожним повтором програма пише номер спроби і затримку. Третій виклик успішний, і результат повертається. У другому запуску сервіс не працює взагалі: після трьох повторів (усього 4 виклики) політика здається і кидає виняток, який ловить `catch`.

## Сценарій 2. Circuit Breaker (база даних)

**Проблема.** База даних "впала" на довший час. Якщо кожен запит і далі намагається з'єднатись і чекає відповіді, програма зависає, а база отримує зайве навантаження.

**Стратегія і чому.** Circuit Breaker. Retry тут не допоможе, бо збій довгий і повтори тільки додадуть навантаження. Після трьох помилок поспіль вимикач розмикається і далі відхиляє запити одразу, не звертаючись до бази. Через 2 секунди він переходить у стан half-open, пропускає один пробний запит, і якщо той успішний, замикається знову.

**Код:**

```csharp
var breakerPipeline = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<DatabaseConnectionException>(),
        FailureRatio = 1.0,
        MinimumThroughput = 3,
        SamplingDuration = TimeSpan.FromSeconds(10),
        BreakDuration = TimeSpan.FromSeconds(2),
        OnOpened = args => { /* лог */ return default; }
    })
    .Build();
```

**Вивід.** Виклики 1–3 завершуються помилкою з'єднання, після третього лог показує `OPEN`. Виклики 4 і 5 відхиляються одразу з `BrokenCircuitException`, база не викликається. Після паузи 2.5 с (база "відремонтована") з'являється `HALF-OPEN`, виклик 6 успішний, і вимикач переходить у `CLOSED`. Виклик 7 проходить як звичайний.

## Сценарій 3. Timeout + Fallback (черга повідомлень)

**Проблема.** Черга повідомлень перевантажена і відповідає дуже повільно. Користувач не повинен чекати без кінця, а повідомлення не повинно загубитись.

**Стратегія і чому.** Timeout обмежує очікування 500 мілісекундами. Fallback спрацьовує, коли час вийшов: повідомлення зберігається локально і буде відправлено пізніше. Ця комбінація не є простим Retry: вона не повторює виклик, а замінює невдачу запасною дією.

**Код:**

```csharp
var queuePipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<TimeoutRejectedException>(),
        FallbackAction = args => Outcome.FromResultAsValueTask("Message saved to local storage")
    })
    .AddTimeout(TimeSpan.FromMilliseconds(500))
    .Build();
```

Fallback додано першим, тобто він зовнішній: він ловить виняток, який кидає внутрішній Timeout.

**Вивід.** Повідомлення 1 і 3 відправляються швидко (100 і 200 мс), результат "Message sent to the queue". Повідомлення 2 потребує 3 секунди, тому за 500 мс спрацьовує Timeout, лог показує `[Fallback]`, і результат — "Message saved to local storage".

## Коли кидати виняток, а коли повертати Result

Виняток доцільно кидати, коли ситуація справді виняткова і метод не може виконати свою роботу: файл не знайдено, з'єднання з базою розірвано, формат даних неправильний. Виняток неможливо випадково проігнорувати, він містить стек викликів. Але він повільніший за звичайний потік виконання.

`Result` (або `bool`, `null`) краще повертати, коли невдача очікувана і трапляється часто: перевірка введених даних, пошук елемента, який може не існувати, перевірка бізнес-правила. Тоді це видно прямо з сигнатури методу, і це швидше. У проєкті є обидва підходи: `Withdraw` кидає `InsufficientFundsException`, якщо коштів немає і операція не може бути виконана, а `TryWithdraw` повертає `false` і текст помилки, коли викликаючий код очікує таку відмову.

Правило: якщо виклик може закономірно "не спрацювати", повертайте результат. Якщо метод не може виконати свій контракт, кидайте виняток.

## Загальні висновки про Polly

**Переваги:**

- не треба писати власні цикли повторів, затримки і лічильники, достатньо описати стратегію
- є готові стратегії: Retry, Circuit Breaker, Timeout, Fallback, а їх можна комбінувати в одному пайплайні
- exponential backoff і jitter вмикаються налаштуваннями
- зручні події (`OnRetry`, `OnOpened` та інші) для логування

**Обмеження:**

- Polly лише допомагає пережити тимчасові збої, а справжні помилки (помилка в коді, неправильні дані) вона не виправить, а повтори тільки приховають їх
- Retry небезпечний для неідемпотентних операцій (наприклад, списання грошей): повтор може виконати дію двічі
- порядок стратегій у пайплайні впливає на результат, тому його треба продумувати
- потрібно правильно підібрати параметри (кількість спроб, затримки, пороги), інакше політика може або не допомогти, або самій створити проблеми
- це додаткова залежність у проєкті
