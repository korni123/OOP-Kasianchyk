# Звіт до самостійної роботи №11

**Тема:** LINQ pipelines: ETL та аналітика.

**Проєкт:** `IndependentWork11`

## Модель даних «Продажі»

- `Sale` (Id, ProductId, Quantity, SaleDate, CustomerId)
- `Product` (Id, Name, Category, UnitPrice)
- `Customer` (Id, Name, City)

**Extract (тестові дані):** `DataGenerator.Generate(60, 80, 600, seed: 42)` створює 60 товарів у 6 категоріях, 80 клієнтів з 8 міст і 600 продажів (кількість 1–5, дати з 01.2025 по 06.2026). Використовується `Random` з фіксованим seed, тому при кожному запуску дані й результати однакові.

**Transform / Load:** чотири пайплайни, кожен — окремий метод з промовистою назвою і **власним** `Stopwatch`. Результат кожного матеріалізується через `.ToList()` всередині заміру — без цього LINQ нічого б не порахував (відкладене виконання), і замір показав би ~0 мс.

## Пайплайни

### 1. `TopProductsByCategory()` — найпопулярніші продукти за категоріями

`GroupBy(ProductId)` → `Select` (сума `Quantity`) → `Join` з `products` (назва, категорія) → `GroupBy(Category)` → у кожній групі `OrderByDescending(TotalQuantity).ThenBy(Name).Take(3)` → `OrderBy(Category)`.

- спочатку групуємо продажі (600 → 60 записів), і лише потім робимо `Join` — так з'єднуються вже агреговані дані, а не кожна продажа;
- `ThenBy(Name)` робить результат стабільним при однаковій кількості.

### 2. `RevenueByCity()` — загальний дохід за містами клієнтів

`Join` з `products` (ціна) → `Join` з `customers` (місто) → дохід `Quantity * UnitPrice` → `GroupBy(City)` → `Sum`, `Count` → `OrderByDescending(TotalRevenue)`.

- два послідовні `Join` — класичний «зірковий» запит: факт (продаж) + довідники (товар, клієнт);
- дохід рахується як `decimal`, щоб не було похибок округлення грошей.

### 3. `SalesByYearAndMonth()` — продажі за місяцями та роками

`Join` з `products` → `GroupBy(new { Year, Month })` (складений ключ — анонімний тип) → `Sum(Quantity)`, `Sum(Revenue)` → `OrderBy(Year).ThenBy(Month)`.

- анонімний тип як ключ групування порівнюється за значеннями полів, тому всі продажі одного місяця потрапляють в одну групу.

### 4. `TopCustomersWithFavoriteCategory()` — власний: топ-5 клієнтів за витратами та їхня улюблена категорія

`Join` з `products` → `GroupBy(CustomerId)` → для кожного клієнта: `Sum` (витрати), `Count` (покупки), **вкладений** `GroupBy(Category)` + `Aggregate` (категорія з найбільшою кількістю) → `Join` з `customers` → `OrderByDescending(TotalSpent)` → `Take(5)`.

- використано 8 різних операторів: `Join`, `GroupBy`, `Select`, `Sum`, `Count`, `Aggregate`, `OrderByDescending`, `Take`;
- `Aggregate` знаходить максимум за один прохід без сортування всієї групи.

## Вимірювання продуктивності

Під час запуску програма виводить час кожного пайплайну, а в кінці — підсумкову таблицю: перший запуск і середнє по 100 повторних запусках.

| Пайплайн | 1-й запуск, мс | Після прогріву, мс |
|---|---:|---:|
| 1. Топ-3 продукти за категоріями | 21.739 | 0.254 |
| 2. Дохід за містами | 5.855 | 0.362 |
| 3. Продажі за роками/місяцями | 5.348 | 0.279 |
| 4. Топ-5 клієнтів + улюблена категорія | 6.770 | 0.684 |

*Заміри з тестового запуску; на іншому ПК числа будуть інші, але співвідношення схоже.*

## Аналіз результатів

**Які фактори вплинули на час виконання:**

1. **JIT-компіляція (найбільший фактор).** Перший виклик у 10–85 разів повільніший за наступні: .NET компілює IL у машинний код при першому виклику кожного методу, лямбди і generic-інстанціювання LINQ-операторів для наших анонімних типів. Пайплайн 1 найповільніший у першому запуску, бо він перший «платить» за JIT `GroupBy`, `Join`, `Select`, `OrderBy`, які потім уже скомпільовані для інших.
2. **Кількість і порядок операцій.** Після прогріву найдорожчий — пайплайн 4: два `Join`, вкладене групування для кожного клієнта і `Aggregate`. Пайплайн 2 дорожчий за 3, бо має два `Join` замість одного.
3. **`Join` реалізований через хеш-таблицю:** LINQ будує `Lookup` по внутрішній колекції (O(m)) і проходить зовнішню (O(n)) — загалом O(n + m), а не O(n·m), як вкладені цикли.
4. **Групування до з'єднання.** У пайплайні 1 спочатку `GroupBy` зменшує 600 продажів до 60 записів, тому `Join` працює з меншими даними.
5. **Сортування** (`OrderBy`) — O(k log k), але k невелике (6 категорій, 8 міст, 18 місяців).
6. **Шум:** збирання сміття (GC), інші процеси, частота процесора — тому для стабільних цифр усереднено 100 запусків.

## Висновки

- LINQ дуже зручний для ETL та аналітики: кожен пайплайн — це декларативний ланцюжок «що отримати», а не вкладені цикли з тимчасовими словниками. Код короткий, читається зверху вниз і схожий на SQL (`JOIN`, `GROUP BY`, `ORDER BY`).
- На сотнях–тисячах записів LINQ працює за частки мілісекунди, тож для типових аналітичних задач у пам'яті продуктивності вистачає з запасом.
- Для коректних замірів треба: матеріалізувати результат (`ToList`), окремий `Stopwatch` на кожен пайплайн, враховувати прогрів JIT і усереднювати кілька запусків.
- Для оптимізації: фільтрувати й групувати якомога раніше, уникати повторного перебору тих самих даних, не викликати `ToList()` всередині ланцюжка без потреби. На мільйонах записів варто думати про PLINQ або виконання на боці БД (Entity Framework перетворює такі ж запити в SQL).
- Читабельність підтримується так: кожен пайплайн в окремому методі з назвою, яка пояснює мету, перенос кожного оператора на новий рядок, осмислені назви властивостей анонімних типів (`TotalQuantity`, `TotalRevenue`).
