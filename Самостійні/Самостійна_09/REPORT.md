# Звіт до самостійної роботи №9

**Тема:** Делегати й лямбда-вирази: власні утиліти для колекцій.

**Проєкт:** `lab9-self-v9`

## Статичний клас CollectionUtils

| Метод | Делегат | Що робить | Аналог LINQ |
|---|---|---|---|
| `Map<TSource, TResult>(collection, Func<TSource, TResult> mapper)` | `Func` | перетворює кожен елемент | `Select` |
| `MaxBy<T, TKey>(collection, Func<T, TKey> keySelector) where TKey : IComparable<TKey>` | `Func` | повертає елемент з найбільшим ключем; для порожньої колекції — `InvalidOperationException` | `MaxBy` (.NET 6+) |
| `Filter<T>(collection, Predicate<T> predicate)` | `Predicate` | повертає елементи, що задовольняють умову | `Where` |
| `ForEach<T>(collection, Action<T> action)` | `Action` | виконує дію для кожного елемента | `List<T>.ForEach` (у LINQ немає) |

## Що демонструє Main

- **`List<Product>`** — імена товарів (`Map`), найдорожчий (`MaxBy`), товари дорожчі за 1000 (`Filter`), вивід усіх (`ForEach`);
- **`List<int>`** — квадрати, «парне/непарне» (`Map` змінює тип `int → string`), додатні (`Filter`), найбільше за модулем (`MaxBy`), сума через замикання в `ForEach`;
- **`List<string>`** — міста у верхньому регістрі, довжини назв, міста на «Л», найдовша назва, перші літери;
- **порівняння з LINQ** — `Map`/`Filter`/`MaxBy` дають ті самі результати, що `Select`/`Where`/`Enumerable.MaxBy` (`True`).

## Звіт

### Чому делегати корисні для створення таких утиліт?

Делегат — це тип «посилання на метод». Завдяки йому метод `Filter` знає **як** перебрати колекцію, але **що** перевіряти — передає той, хто викликає. Алгоритм (цикл, збирання результату) написаний один раз, а змінна частина (умова, перетворення, дія) підставляється ззовні. Без делегатів довелося б писати окремі `FilterExpensiveProducts`, `FilterPositiveNumbers`, `FilterCitiesStartingWithL`… Разом з generic-параметрами (`T`, `TResult`, `TKey`) один метод працює з будь-яким типом даних.

Вбудовані делегати покривають усі випадки:
- `Func<T, TResult>` — приймає елемент, повертає результат (`Map`, `MaxBy`);
- `Predicate<T>` — приймає елемент, повертає `bool` (`Filter`);
- `Action<T>` — приймає елемент, нічого не повертає (`ForEach`).

### Як лямбда-вирази спрощують виклик цих методів?

Без лямбд для кожної умови треба було б оголошувати окремий іменований метод і передавати його назву. Лямбда пишеться прямо в місці виклику: `CollectionUtils.Filter(products, p => p.Price > 1000)` — одразу видно, що фільтрується. Компілятор сам виводить типи (`p` — це `Product`, `TResult` — `string`), тому generic-параметри вказувати не потрібно. Лямбди також можуть використовувати змінні ззовні (замикання) — так у `ForEach(numbers, x => sum += x)` змінюється локальна змінна `sum`.

### Порівняння з вбудованими LINQ-операторами

| | Мої методи | LINQ |
|---|---|---|
| Виклик | `CollectionUtils.Filter(list, x => ...)` | `list.Where(x => ...)` — методи розширення, можна будувати ланцюжки |
| Виконання | **жадібне** — одразу створюється `List` з результатом | **відкладене** (`yield return`) — нічого не рахується, поки результат не перебирається |
| Пам'ять | завжди проміжний список | без проміжних колекцій |
| Делегат для фільтра | `Predicate<T>` | `Func<T, bool>` (+ перевантаження з індексом) |
| Перевірки | мінімальні | перевірка на `null`, оптимізації для масивів і списків |
| `MaxBy` порожньої колекції | `InvalidOperationException` | для посилальних типів повертає `null` |

**Висновки:** результати збігаються, тож логіка реалізована правильно. Власні методи корисні для розуміння того, як LINQ працює всередині, і коли потрібна специфічна поведінка (наприклад, логування, жадібне виконання, своя обробка порожньої колекції). У реальних проєктах краще використовувати LINQ — він лінивий, оптимізований, перевірений і всім знайомий. Головна ідея обох підходів однакова: узагальнений метод + делегат + лямбда = повторне використання логіки.
