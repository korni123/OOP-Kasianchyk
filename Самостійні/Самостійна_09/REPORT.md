# Звіт до самостійної роботи №9

## Чому делегати корисні для створення таких утиліт?

Делегат дозволяє передати метод як параметр. Наприклад, `Filter` сам перебирає колекцію і збирає результат, а умову фільтрації передає той, хто його викликає. Завдяки цьому один метод замінює багато окремих (`FilterExpensiveProducts`, `FilterPositiveNumbers` …), а разом з generic-параметрами працює з будь-яким типом даних.

Використані делегати:
- `Func<T, TResult>` — приймає елемент і повертає результат (`Map`, `MaxBy`);
- `Predicate<T>` — приймає елемент і повертає `bool` (`Filter`);
- `Action<T>` — приймає елемент і нічого не повертає (`ForEach`).

## Як лямбда-вирази спрощують виклик цих методів?

Без лямбд для кожної умови треба писати окремий метод. З лямбдою умова пишеться прямо у виклику:

```csharp
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Компілятор сам визначає типи, тому їх не треба вказувати. Лямбда також може змінювати зовнішні змінні — так у `ForEach(numbers, x => sum += x)` рахується сума.

## Порівняння з LINQ

| | Мої методи | LINQ |
|---|---|---|
| Виклик | `CollectionUtils.Filter(list, ...)` | `list.Where(...)` — можна будувати ланцюжки |
| Виконання | одразу створює новий список | відкладене — рахується, коли результат перебирають |
| `MaxBy` для порожньої колекції | виняток | для класів повертає `null` |

Результати моїх методів і LINQ збігаються (у програмі перевірка виводить `True`).

## Висновки

Власні методи допомагають зрозуміти, як LINQ працює всередині: це узагальнений метод + делегат + лямбда-вираз. У реальних проєктах краще використовувати LINQ — він оптимізований, підтримує ланцюжки і відкладене виконання. Свої утиліти мають сенс, коли потрібна особлива поведінка, якої немає в LINQ.
