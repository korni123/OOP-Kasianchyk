# Звіт до самостійної роботи №12

## Експерименти з продуктивністю

Колекція `List<int>` з випадковими числами, розміри: 1M, 5M і 10M елементів. Три операції:
- **легка:** `x * 2` для парних чисел;
- **середня:** перевірка числа на просте;
- **важка:** 40 ітерацій `Math.Sqrt`, `Math.Sin`, `Math.Log` для кожного елемента.

Кожна операція виконувалась через LINQ (`.Where().Select()`) і PLINQ (`.AsParallel().Where().Select()`), час вимірювався `Stopwatch`.

| Розмір | Операція | LINQ, мс | PLINQ, мс | Прискорення |
|---:|---|---:|---:|---:|
| 1M | легка | 14.6 | 81.3 | 0.18× |
| 1M | середня | 247.0 | 145.6 | 1.70× |
| 1M | важка | 377.5 | 286.3 | 1.32× |
| 5M | легка | 66.1 | 94.0 | 0.70× |
| 5M | середня | 907.5 | 482.6 | 1.88× |
| 5M | важка | 1799.2 | 1056.0 | 1.70× |
| 10M | легка | 135.5 | 195.0 | 0.69× |
| 10M | середня | 1802.9 | 1009.5 | 1.79× |
| 10M | важка | 3823.3 | 1995.1 | 1.92× |

На іншому комп'ютері числа будуть інші: чим більше ядер, тим більше прискорення в PLINQ.

## Коли PLINQ швидший, а коли ні

- **Легка операція — PLINQ повільніший.** Сама операція займає мізерний час, а PLINQ витрачає час на поділ даних між потоками і об'єднання результатів. Ці витрати більші за користь.
- **Середня і важка операції — PLINQ швидший.** Кожен елемент обробляється довго, і робота ділиться між ядрами процесора.
- **Розмір колекції.** На 1M елементів виграш менший, ніж на 5M і 10M, бо витрати на запуск паралельної обробки ще помітні.

## Сценарій з побічними ефектами

**Проблема:** рахуємо парні числа через спільну змінну всередині PLINQ:

```csharp
int counter = 0;
data.AsParallel().ForAll(x =>
{
    if (x % 2 == 0) counter++;
});
```

Правильна відповідь — 2 500 345, а програма щоразу видає інше число (наприклад 1 787 354, 1 891 478, 1 783 928…). Причина: `counter++` — це три дії (прочитати, додати 1, записати). Два потоки одночасно читають однакове значення, і одне збільшення губиться.

Так само зі спільним `List<int>`: `List.Add` з різних потоків губить елементи або кидає виняток `ArgumentOutOfRangeException`.

**Виправлення:**

```csharp
lock (locker) { lockCounter++; }                  // тільки один потік за раз
Interlocked.Increment(ref interlockedCounter);    // атомарне збільшення
ConcurrentBag<int> bag = new ConcurrentBag<int>(); // потокобезпечна колекція
int count = data.AsParallel().Count(x => x % 2 == 0); // без побічних ефектів
```

Усі способи дають правильний результат 2 500 345:
- `lock` — найповільніший, бо потоки чекають один одного;
- `Interlocked` — швидший, підходить для лічильників;
- `ConcurrentBag` — підходить, коли треба зібрати елементи;
- `.Count()` без побічних ефектів — найшвидший і найкращий варіант.

## Висновки

1. PLINQ варто використовувати, коли операція над кожним елементом довга, а елементів багато.
2. Для простих операцій PLINQ може бути повільнішим за звичайний LINQ, тому рішення треба приймати після вимірювань на різних розмірах даних.
3. Усередині PLINQ не можна змінювати спільні змінні та звичайні колекції — результат буде неправильним.
4. Краще використовувати вбудовані методи (`Count`, `Sum`, `ToList`), а якщо спільні дані потрібні — `Interlocked`, `ConcurrentBag` або `lock`.
