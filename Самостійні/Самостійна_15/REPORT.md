# Звіт до самостійної роботи №15

**Чому делегати корисні для створення таких утиліт?**

Делегат дозволяє передати в метод не дані, а дію. Метод `Map` вміє перебирати колекцію, але не знає, що саме робити з кожним елементом. Це визначає делегат `Func`, який передає той, хто викликає метод. Тому один метод `Map` підходить і для чисел, і для рядків, і для продуктів, і його не треба переписувати для кожного випадку.

**Як лямбда-вирази спрощують виклик цих методів?**

Без лямбда-виразів для кожної дії довелося б писати окремий метод з іменем і потім передавати його. Лямбда-вираз пише дію прямо в місці виклику, коротко: `p => p.Price > 1000`. Лямбда також бачить змінні навколо себе, наприклад змінну `sum` у `ForEach`, тому не треба передавати їх окремо.

**Порівняння з вбудованими LINQ-операторами**

| Мій метод | LINQ-аналог | Відмінності |
|---|---|---|
| `Map` | `Select` | Мій метод одразу будує список, а `Select` виконується відкладено, коли починають перебирати результат |
| `Filter` | `Where` | Те саме: мій метод повертає готовий список, `Where` — відкладений запит |
| `MaxBy` | `MaxBy` (.NET 6+) | Логіка однакова. Мій метод для порожньої колекції кидає `InvalidOperationException` |
| `ForEach` | `List<T>.ForEach` | Мій метод працює з будь-яким `IEnumerable<T>`, а не тільки зі списком |

Вбудовані LINQ-оператори швидші і краще перевірені, мають більше можливостей, наприклад відкладене виконання, яке не створює зайвих списків. Свої методи корисні, щоб зрозуміти, як працюють делегати і як працює LINQ всередині.

**Висновок**

Делегати і лямбда-вирази дозволяють написати один узагальнений метод і використовувати його з будь-якими типами та будь-якою логікою. Власні методи `Map`, `Filter`, `MaxBy`, `ForEach` працюють так само, як відповідні оператори LINQ.
